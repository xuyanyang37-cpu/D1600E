# Dell/Delta D1600E 00.3D.67 — I2C1 / CRC-8 重新核验

## 结论摘要

本轮首次从固件程序映像中提取出两张完整的 CRC-8 半字节查找表。它们逐项精确匹配 CRC-8 多项式 0x07 的低半字节表和高半字节表。该 CRC 例程位于 `PC=0x00332A`，并被 I2C1 中断路径调用，因此它是该固件 PEC 实现的强候选。

但目前还没有证明 CRC 初值、地址字节是否进入 CRC、接收 PEC 的最终比较点、发送 PEC 的追加时机。因此暂不把“完整 PMBus PEC 收发流程已还原”作为结论。

## 1. 纠正此前反汇编报告中的错误

此前报告中以下解释不成立，现明确撤回：

- `PC=0x006FC0` 的 `B3C201` 不是读取 `I2C1RCV`。按 dsPIC33F 指令字段，它是 `MOV.B #0x20,W1`。
- `PC=0x0065D8` 和 `0x0065EE` 的 `BE020A` 属于 `MOV.D` 双字寄存器/间接寻址指令形式，不能解释为直接访问 SFR `I2C1ADD=0x020A`。
- `PC=0x00102A` 的 `200206` 是 `MOV #0x0020,W6`，不是对 `I2C1CON=0x0206` 的写入。
- 因此目前没有从这几个指令位置证明 I2C1ADD 的初始化值，也没有从固件中确认 7-bit 地址 0x58。

仍然成立的 I2C1 证据是：`PC=0x006FB8`、`0x006FBE`、`0x006FE0`、`0x006FE6`、`0x00700E`、`0x007014`、`0x007026`、`0x00702C` 等位置出现 `BFC208`，它符合直接读取 SFR `I2C1STAT=0x0208` 的编码；ISR 随后检查 bit 2（R_W）和 bit 5（D_A）。

## 2. CRC-8 表的位置和数据

CRC 更新函数 `0x00332A` 装载了两个 PSV 数据空间指针：

- `0x9892`
- `0x9882`

dsPIC33FJ64GS606 的 PSV 区为数据空间 `0x8000–0xFFFF`；PSVPAG 选择程序空间 16K-word 页，低 15 位数据地址映射到该页的对应程序地址。PSVPAG 复位值为 0。固件在启动辅助代码 `0x000C62` / `0x000C6E` 对 CORCON bit 2（PSV）执行清除/置位操作。

因此在 PSVPAG=0 时：
- PSV 地址 `0x9882` 对应程序 PC `0x001882`
- PSV 地址 `0x9892` 对应程序 PC `0x001892`

从原始 4-byte-slot 程序映像读取这些位置的 16-bit program-word 数据字节，得到：

**低半字节表（PC 0x1882，对应 PSV 0x9882）：**
```
00 07 0E 09 1C 1B 12 15
38 3F 36 31 24 23 2A 2D
```

**高半字节表（PC 0x1892，对应 PSV 0x9892）：**
```
00 70 E0 90 C7 B7 27 57
89 F9 69 19 4E 3E AE DE
```

使用独立脚本按多项式 0x07 重新生成两张 16 项表后，两张表都逐字节完全相同，非近似匹配。

## 3. CRC 更新函数 0x00332A

原始指令序列：

```
00332A B6D3F0
00332C B7F3F0
00332E FB8000
003330 DE0144
003332 60006F
003334 298921
003336 78C162
003338 298821
00333A 78C060
00333C 694000
00333E FB8000
003340 060000
```

关键行为（按 dsPIC33F 指令编码字段核对）：

- `B6D3F0`：对数据变量 `0x13F0` 与 W0 执行 XOR，形成 CRC 状态与输入字节的组合值。
- `B7F3F0`：把 W0 写回 `0x13F0`，保存中间值。
- `DE0144`：对 W0 执行右移 4 位，形成高半字节索引。
- `298921` / `78C162`：装载 `0x9892` 表基址并进行索引读取。
- `298821` / `78C060`：装载 `0x9882` 表基址并进行索引读取。
- `694000`：将两次查表结果 XOR。
- 返回更新后的 8-bit CRC 结果（函数还包含字节宽度处理指令）。

由两张查表的逐项内容可确定其数学核心为 CRC-8、MSB-first、多项式 0x07 的半字节查表算法。标准形式可写为：

```c
uint8_t crc8_07_update(uint8_t crc, uint8_t data)
{
    uint8_t x = crc ^ data;
    return crc8_hi[x >> 4] ^ crc8_lo[x & 0x0F];
}
```

注意：固件中的低半字节掩码寄存器上下文、CRC 初值重置位置，以及最终返回值是否与收到的 PEC 比较，仍需继续追踪；上面是查表算法的标准等价形式，不是声称已经完整还原所有调用约定。

## 4. 为什么它与 PMBus PEC 高度相关

- `0x00332A` 的直接调用点包括 `0x006F86`、`0x006FDA`、`0x006FF6`；这些调用位于 SI2C1 ISR 或其紧邻辅助路径。
- 该函数使用的 CRC-8 多项式为 0x07。
- SMBus 3.2 规范定义 PEC 为 CRC-8，生成多项式为 `x^8+x^2+x+1`（即省略最高项后的 0x07），按总线收到的位序计算；PEC 覆盖地址、命令和数据，不覆盖 START/STOP/ACK/NACK 等总线控制位。

这三点构成“固件 I2C1 路径调用 SMBus/PMBus PEC 算法”的强证据，但尚未构成完整事务证据。下一步要确认地址字节是否在相同 CRC 状态中更新、PEC 字节的接收/发送位置，以及 CRC 状态在 START/STOP/Repeated START 时如何清零或保留。

## 5. 下一步需要追踪的函数

1. `0x006F6A`：它调用 `0x00332A`，并在 I2C1 ISR 路径附近被调用，优先检查 CRC 状态初始化、更新和读取。
2. `0x00328C`：确认 I2C 接收/发送缓冲区及事务状态。
3. `0x00280A`：循环处理 0x55 次并调用 CRC 更新函数；要确认它是配置块校验还是 I2C 数据块处理，不能先入为主认定是 PEC。
4. `0x006F5E` / `0x006F64`：追踪 I2C 事务状态及地址/数据阶段辅助处理。
5. I2C1 设备地址初始化和命令分派：目前仍未确认，尤其不能把用户实测 0x58 写成固件已证实的地址。

## 6. ESP32 可复用的已确认算法片段

以下是由固件查表数据验证出的 CRC-8/0x07 数学算法，可作为 ESP32-S3 协议层的 PEC 算法候选；在确认固件 CRC 初值和帧覆盖范围前，不要直接把它用于所有命令事务：

```cpp
uint8_t pmbusPecUpdate(uint8_t crc, uint8_t data) {
    crc ^= data;
    for (uint8_t i = 0; i < 8; ++i) {
        crc = (crc & 0x80)
            ? (uint8_t)((crc << 1) ^ 0x07)
            : (uint8_t)(crc << 1);
    }
    return crc;
}
```

上面逐位算法用于独立验证标准 CRC-8/0x07；固件实际采用的是两张半字节查表。正式接入 ESP32 时，应使用同一初值、字节顺序和帧覆盖规则，并用实测总线事务做交叉验证。

## 7. 安全边界

本分析只针对离线固件，不执行烧录、不对未知 PMBus 厂商命令进行写入。固件头部 `095HR5A00` 与板上标识 `95HR5A05PS` 的兼容关系仍未证实。
